随机户型，不是随机画墙。
先让空间有逻辑，
再让机器人走得通。

从房间关系图、几何分区到可验证的仿真场景：一份面向 Wizard 机器人与资产工作流的实用指南。

单文件 · 离线可运行Seed 可复现演示拓扑 → 几何 → 资产 → 验证含 JSON 与 Schema 导出

推荐起点：规则与约束，而不是先训练模型。

先做一个可控、可解释、失败可定位的 2D 生成器。用模板或受约束分区产生候选，用独立验证器筛选，最后再接家具与目标仿真器。

当目标是批量生产机器人训练环境，真正的交付物应是结构化场景 + 验证报告 + 可复现配置，而不只是漂亮的平面图。

本文是一套建议架构。未审查或修改 Wizard 源码，也未确认已有生成器或仿真适配器。演示是独立教学实现，不是 ProcTHOR 或任何模型的复现。

01 /

先分清，你要生成哪一层？

TOPOLOGY

房间怎么连接

卧室是否经走廊到客厅？厨房和餐厅是否相邻？用图描述功能关系，先不决定每一条墙的位置。

GEOMETRY

房间是什么形状

给每个房间分配面积、边界与位置，再构造唯一的共享墙、真实厚度以及门窗洞口。

SIMULATION

场景能不能执行任务

落地资产、碰撞体、门状态和机器人起点；验证任务目标可达、接触稳定与所需交互。

本文假设：第一版为单层、正交住宅；输入为面积/外轮廓、房间清单和 seed，输出供仿真与算法研究使用。楼梯、多层、结构荷载、机电、采光和当地建筑规范需另立模型；文中尺寸均为演示参数或工程配置示例，不是法规要求。
方法适合什么主要边界建议角色
模板 + 受约束分区 / BSP快速批量生成；固定外轮廓与房间数量BSP 递归切分易确保分区不重叠，但只覆盖特定切割式布局；单靠切分不保证住宅语义和门图合理MVP 首选本指南示例为“走廊骨架 + 两侧分区”，不是通用 BSP 求解器
房间图 + 约束求解指定面积、邻接、朝向、净宽等可解释要求不保证任意输入有解；需限制模型规模、设超时、记录不可行原因第二阶段；CP-SAT 采用整数变量，可用厘米网格建模 [6]
Graph2Plan / House-GAN学习真实户型分布，生成具有风格与多样性的候选需要数据与训练/推理环境；输出仍要几何清理与独立验收增强候选，不取代硬约束验证 [4] [5]
ProcTHOR参考面向具身智能的完整室内场景生成流水线官方目标为 AI2-THOR；资产、schema 与运行时有特定约定复用其阶段设计，或在 AI2-THOR 中先建立基线；跨引擎需要适配 [1] [2]

方法选择是本文的工程建议，并非论文之间的统一基准排名。BSP 生成和基于图的约束生成可以组合，不必互斥。

先动手：一个可复现的小户型实验

改变 seed、房间数和外轮廓，观察分区。固定输入会得到相同 JSON。示例固定中部交通骨架，随机化两侧分区与功能分配，刻意让算法保持可读。

客厅厨房卫生间卧室 / 书房窗线开放门洞

图上墙线仅用于表达分区，不含物理墙厚。深色块是家具占位符；所有门洞开放，无门扇、门框或物理仿真。窗只沿上下外边界布置。

—外轮廓面积 · 忽略墙厚
—功能房间 + 1 条走廊

本次示例检查

    “门图连通”仅说明房间节点有连接。它不代表家具后的自由空间连通、机器人能转弯、门能打开或建筑合规。

    发布前验证：9,018 组 seed / 房间数 / 外轮廓组合通过确定性与五项规则检查；54 组通过 JSON Schema。范围仅限此演示，不是连续空间或建筑合规证明。
    这个示例到底做了什么，没做什么？

    采用固定版本的 Mulberry32 伪随机数生成器。先分出 1.40 m 宽的水平走廊，再把上下两排分成共 4–6 个房间；功能房间最小边为 2.40 m。每个房间放一扇 0.90 m 示意门和一段 1.20 m 外窗，再放一个二维占位块。这些是算法参数，不是居住设计标准。

    已实现：可复现整数 seed、房间分区、门/窗边界归属、门图、占位矩形、JSON / SVG 导出、五项几何与图检查。

    未实现：任意多边形、真实住宅面积分配、隐私/干湿/动静分区、墙厚、门扇扫掠、3D 家具、资产绑定、机器人半径、NavMesh、物理测试和建筑合规。走廊占比偏大、房间类型随机分配等现象正是后续约束需要解决的问题。

    03 /

    完整生成器：六个阶段，一个闭环

    01 / SPEC采样需求seed · 面积 · 房型
    02 / GRAPH定义拓扑邻接 · 通行 · 偏好
    03 / SHAPE求解几何边界 · 面积 · 墙体
    04 / OPENINGS放门窗共享墙 · 外墙
    05 / OBJECTS摆家具锚定 · 占地 · 通路
    06 / VERIFY验收与导出拒绝 · 修复 · 复现
    ① 采样需求
    先规定分布

    输入至少包含：外轮廓或面积区间、卧室数量、房间类型、面积范围、长宽比上限、入口候选、机器人模型以及约束优先级。不要把“每个变量独立均匀采样”当作住宅分布：房间数应与面积联动，厨房、卫生间和采光空间有不同位置偏好。

    将 seed_layout、seed_furniture、seed_visual 分流并固定派生规则。这样换沙发或灯光，不必连带改变户型。生产端同时记录生成器提交、配置哈希、资产清单版本、求解器版本与参数。

    ② 先建两张图
    邻接 ≠ 可通行

    邻接图 Gadj：房间之间是否共享足够长的一段墙；接触一个角不算可开门邻接。门图 Gdoor：实际设有可通行开口的房间连接；它应是几何允许邻接的子图。

    “必须有门”“必须相邻但不设门”“尽量靠近”“不得直接连通”要分开表示。例如卧室的可达路径不应依赖穿过另一间卧室，可作为项目偏好或硬约束；不是普适法规结论。先检查入口可达，再处理卧室私密性、厨房/餐厅关系与服务区聚合。

    ③ 从图到几何
    求解，不是装饰

    第一版可以从“交通骨架 + 分区模板”采样；升级版为每个房间设置 x, y, w, h（整数网格），约束边界内、内部不重叠、面积区间、长宽比与共享边长度。目标图不一定能嵌入给定边界，不可行时应回溯或重新采样，而非偷偷丢掉约束。

    若用 CP-SAT，所有变量与约束表达需按整数建模；用厘米或合适网格避免任意浮点。求解状态要区分 INFEASIBLE 与 UNKNOWN：超时没找到解，不等于已证明无解。面积乘积等关系需按求解器能力建模。[6]

    分区之后再建立共享墙的规范化 ID、两侧房间和厚度；同一墙只建一次。加墙厚后重新算净面积、门洞净宽与室内可用多边形，不能沿用“零厚度”通过的结果。

    ④ 门窗落位
    必须有承载边界

    每条必需门边先找共享墙候选，要求有效长度覆盖门宽、两端余量及结构限制。沿墙参数化开口，保留宿主墙 ID、位置、高度、门扇方向和初始状态。入口必须连接外部和合法入口房间。

    窗从外墙候选中选，按房间需求考虑长度、窗台高和间距，避免与门、角点和家具冲突。ProcTHOR 官方代码也将门连接与房间关系结合，并从接触外部的墙选择窗候选；这里只借鉴其分阶段思路。[3]

    ⑤ 家具与资产
    先占地，后细节

    先按房间类型选类别：床、沙发、桌、柜、灶台等；再用墙边、角落、中心或支撑表面作为锚点。大件先放，小件后放；候选位姿必须落在可用区域内，并扣除已有占地、门扇扫掠区、通行余量与任务操作区。

    对 Wizard 资产建议新增一层资产适配表：稳定 asset_id、实际尺寸、朝向、原点、支撑面、简化碰撞体、可交互关节、许可/来源。占位框不等于真模型包围盒；替换成真实资产后要重新验证。本文未读取资产内容或确认这些字段已存在。

    ⑥ 验收与反馈
    失败是数据

    验证失败应给出可定位的原因：ROOM_OUT_OF_BOUNDS、NO_SHARED_WALL_FOR_DOOR、DOOR_CLEARANCE_BLOCKED、TARGET_UNREACHABLE。小范围问题优先局部重摆；结构性矛盾回退上游；达到配置的尝试上限后明确失败，不无限循环。

    把失败样本和生成配置保存为回归测试。统计候选数、接受率、失败类别、生成时间分位数、房间面积分布、图结构多样性与任务可达率，而不是只挑最好看的几张图。

    硬约束先过滤 → 再最小化软代价：
    E = λ₁ · 面积偏差 + λ₂ · 邻接偏好违约 + λ₃ · 过长动线 + λ₄ · 狭长房间 + λ₅ · 不合理服务区距离

    这是建议的目标函数结构，不是已训练模型。先确保所有硬约束成立，再对合法候选排序；不要靠一个加权总分允许“穿墙但其他分数很高”的方案通过。

    04 /

    如何借鉴已有工作，而不误读能力

    PROCTHOR / END-TO-END REFERENCE

    学习流水线，不要只抄一张图

    ProcTHOR 将房间规格、外形、结构、门、材质/灯光、大物体与小物件组织成室内场景生成流程。官方框架面向 AI2-THOR 的可交互 3D 环境。[1] [2]

    其公开户型实现并非简单 BSP：按层次房间规格在网格上生长，先矩形扩张，再允许 L 形扩张，并对候选打分。对自己的 MVP，无需一开始复制全部复杂度。[3]

    LEARNED MODELS / CANDIDATE PROPOSERS

    模型负责提出方案，验证器负责验收

    Graph2Plan 接收布局图和建筑边界，结合检索/编辑流程，生成栅格布局与精炼房间框；House-GAN 从房间类型、数量与邻接关系生成轴对齐房间框。[4] [5]

    这些表示有助于生成多样候选，但房间框还不是带有墙厚、门窗、碰撞体的完整仿真场景。模型评测上的兼容性指标也不等于每个样本都满足所有硬约束。

    不要把图像生成当成几何生成器。文字生成户型图片适合讨论风格，不适合作为唯一的碰撞或任务真值。若用 LLM，优先让它输出可验证的房间清单、关系图或参数；若用图像/生成模型，输出必须再结构化、校正并验收。
    05 /

    “能画出来”到“机器人能用”，差一套验收

    至少分四层检查。每一层都应明确机器人形态、门状态、分辨率和任务定义；上层通过不意味着下层自动通过。

    层级必须检查不能据此宣称
    L1 · 几何与拓扑房间合法多边形、无内部重叠、边界覆盖、墙唯一性；门在宿主墙内；门图从入口连通不能据此宣称机器人能通过所有房间
    L2 · 自由空间按机器人碰撞外形扩张墙/家具，或在配置空间检查；门洞净宽、门扫掠区、通道、转弯区；起点到任务点连通2D 圆盘近似不覆盖机械臂、非圆形底盘姿态、门交互和动态障碍
    L3 · 任务可达在目标仿真器里采样可达起点；导航到每类任务区域；验证感知视点、抓取/操作范围、遮挡与门状态路径存在不代表策略能成功；能到房间不等于能看到或操作目标物
    L4 · 物理与运行碰撞体与视觉一致，质量/惯量与静动态分类正确；稳定落地、关节限位、接触、短时运行；记录引擎与参数仿真通过不是现实建筑安全、无障碍或法规合格证明

    门宽要看净宽，而非画线长度

    对简化圆盘底盘，配置示例可写为：clear_width ≥ 2 × radius + 2 × margin。例如半径 0.25 m、每侧余量 0.10 m，对应 0.70 m 的几何要求。

    这只是静态圆盘近似的计算示例，不是实际机器人或建筑规范推荐值。必须考虑门框、门扇、转弯、误差、姿态与目标机器人的完整碰撞体。

    栅格 BFS 有分辨率边界

    粗网格可能漏掉窄通路，也可能因占用栅格方式产生误判。报告要写明栅格步长与障碍膨胀参数；关键狭窄区域用更细检测或仿真器碰撞查询复核。

    AI2-THOR 的 GetReachablePositions 使用由 gridSize 决定的网格 BFS。ProcTHOR 的公开验证检查各房间可达采样点，不能推广为任意机器人或任意门状态下的保证。[7] [3]

    建议的验收报告：对每个场景保存 geometry_pass、door_graph_pass、navigation_pass、physics_pass，以及适用机器人、门状态、检测分辨率与失败列表。未执行项用 not_run，不要用默认 true。
    06 /

    让 JSON 成为唯一几何事实来源

    把 2D 预览和 3D 场景都从同一结构化数据生成。避免“SVG 看起来对，但仿真器里又手动摆一套”的双份真值。

    基础字段

    • 复现：schema / generator 版本、seed、PRNG、全部配置、资产清单与校验哈希。
    • 坐标：单位、手性、上轴、原点、朝向；这里统一米制、XY 地面、Z 向上。
    • 几何：边界、多边形房间、共享墙与厚度；开口引用宿主墙和两侧 room ID。
    • 资产：实例 ID、资产 ID/版本、位姿、缩放、碰撞/物理配置、语义与交互状态。
    • 任务：机器人、出生点、目标采样规则、难度与数据集 split。
    • 验收：独立结果、版本、参数和失败证据。

    Schema 检查什么？

    JSON Schema 可以约束字段、类型、枚举、数组维度与数值范围；但“多边形不相交”“房间引用存在”“门图连通”“机器人可达”仍需程序验证。

    本文件内置一个适用于演示 JSON的 Draft 2020-12 Schema，可下载后用于结构校验。它不是生产端全量 schema；完整系统应新增墙体、3D 位姿、资产与验收元数据。

    演示 JSON 的 asset_id: null 明确表示尚未绑定实际 Wizard 资产。下载文件保存在浏览器默认下载位置。

    08 /
    推荐实施顺序：先闭环，再扩大自由度
    每一阶段有明确“完成标准”，不要同时引入新户型、新资产与新引擎，导致失败无法归因。
    

    阶段一 · 结构化 2D 基线
    矩形边界、有限房型、seed、房间/门图、简单门窗、JSON + SVG。用模板或受约束切分；先不接真实家具。
    完成标准：固定测试集可复现；每个接受样本通过几何与门图检查；失败有原因和尝试上限。
    阶段二 · 机器人约束与资产
    明确机器人碰撞外形与任务点；建立资产适配表，从占位框换成实际尺寸与碰撞代理；加入摆放、净空和路径检测。
    完成标准：指定机器人/门状态下，必需任务区域可达；换资产后重验，不依赖“看起来放得下”。
    阶段三 · 单一仿真器闭环
    先选一个目标运行时，自动导出、加载、检查碰撞、采样起点、跑短测试。保存最终场景与资产版本。
    完成标准：自动 smoke test 有可复核报告；2D 与 3D 的墙、洞口、坐标和语义一致。
    阶段四 · 多样性与学习式增强
    加入 L 形外轮廓、多种交通结构、软约束求优、ProcTHOR 式扩张或学习式候选；用接受率和任务覆盖评估收益。
    完成标准：新方法改善真实指标；按几何结构/资产家族划分训练与测试，防止近重复样本泄漏。
    

    对 Wizard 的最小下一步：先确认一个目标仿真器、机器人外形/通行尺寸，以及资产尺寸和碰撞元数据是否可读。然后实现 generate(config) → scene.json、validate(scene, robot) → report、export(scene, engine) 三个独立接口。本文只整理路线与演示，未修改项目。
